7. ARCHITECTURE RULES

Use the supplied pattern as a starting point and justify deviations:

- Control register:
  Owns controls, threshold specifications, owners, and versions.
  Stays outside the live request path.

- Evaluator:
  Stateless comparison of supplied observations/context against a pinned specification.
  Returns a decision and reasons.

- Enforcement point:
  Invokes the evaluator and applies allow, deny, or alert behavior.

- Telemetry store:
  Retains observations without deciding control satisfaction.

- Evidence ledger:
  Binds records to controls, versions, runs, and actors without interpreting them.

- Control-test/query tool:
  Reconciles evidence and recomputes results for a specified scope.

Distinguish a runtime evaluator’s action decision from a control tester’s dated assessment of an entire run or window. Keep these outputs separately typed.

Load and pin specifications outside individual model/tool request paths.

Define historical version lookup so old evidence is never tested accidentally against today’s threshold.

Keep telemetry, ledger writes, and register access asynchronous/off the critical request path as described in the masterclass.

Explain durable delivery, buffering, retries, and reconciliation so asynchronous processing does not hide lost records.

Design one logical contract with adapters for:
- evaluate(): synchronous decisions at an interceptable enforcement point.
- emit(): asynchronous events.
- callback(): delayed decisions or human approval outcomes.
- pull(): scheduled collection and reconciliation.

Implement only the transports needed for the chosen scope. Show how the others fit without claiming they are built.

The architecture should accommodate static, scheduled, event-driven, in-transaction, and continuous checks without forcing every control into a request hook.

Separate required architecture properties from optional service choices. Do not add infrastructure merely to make the design look enterprise-scale.
