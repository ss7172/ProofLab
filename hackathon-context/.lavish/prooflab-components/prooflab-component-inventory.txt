PROOFLAB V4 — COMPLETE COMPONENT INVENTORY

Purpose: name the parts before tracing the story. This is the logical decomposition of the architecture already proposed, not123 separately deployed services and not a new implementation plan. The 16 groups and their123 subcomponents share one assurance package wherever practical. No live integrations are demonstrated; actual completed controls remain0/3.

Labels:
Provided = described in the workshop; access and actual behavior still require verification.
Build = our proposed application code/module/contract, not necessarily a service.
Configure = adapt an existing platform, endpoint or repository capability if enabled.
Optional = deferred extension or conditional bonus; not needed for the first complete implementation of the three control tests.
Mixed items explicitly say when only their interface or polished variant is optional. 'Minor component' means a subcomponent, not low importance.

PHYSICAL DEPLOYMENT, SEPARATE FROM LOGICAL GROUPS
1. Provided telecom workflow in ServiceNow/AWS with its existing tools, gateways and model route.
2. One ProofLab Python distribution: source adapters and ingestion/assessment worker; query/investigator entry point; shared controls, policies, validation and export modules. These entry points can share a permitted host; they do not require one service per module.
3. Optional permitted in-path admission hook/wrapper and transactional run/attempt state for preventive Control16.
4. Judge client: local CLI and optional HTML UI, with authenticated cloud access or a portable offline bundle.
5. External platform dependencies: approved NVIDIA endpoint, ServiceNow governance, allowed compute and storage. DynamoDB/S3 are conditional mappings; SQLite is the local query index. Calling Nemotron does not require us to deploy model weights or GPUs.

TRACING ROADMAP
A. Prepare the rules and permitted platform: M04 + M16.
B. Follow one live fault-resolution workflow: M01 -> M03 -> M02, with M10 only when preventive enforcement is implemented.
C. Follow its records into the evidence workspace: M05 -> M06. Acquisition runs alongside the subject workflow.
D. Assess the controls: M07/M08/M09 -> M12; M14 delivers applicable findings asynchronously. C9 has scheduled windows, not only per-run calls.
E. Answer a judge: M13 -> M11 -> M12 -> affected control reassessment -> M13; source versions and accepted-input revisions stay explicit.
F. Independently reproduce and submit: M15, using the same accepted records and calculations.
These are separate views of concurrent workflows, not one serial request through all16groups.

FIRST STORY BEAT — BEFORE ANY CONTROL DECISION
Illustration only, not an actual run: a customer reports that their mobile data service has stopped working. The supplied ServiceNow customer/ticket agent (M01.1) receives or is triggered by the permitted fault request. It has a business case/ticket identity and context. It is part of the subject being assessed; it is not our evidence investigator.
Before the first governed action, the trusted lifecycle integration (M03) creates or resolves the canonical run identity, for example FM-001, under the authorized team and the predeclared policy bundle (M04).
