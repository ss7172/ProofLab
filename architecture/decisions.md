# ProofLab decisions D1–D16 (team iFabric)

Written 2026-10-05 by the architect subagent, with the final architecture (`architecture/ARCHITECTURE.md`, §13). The options and their evidence are in `architecture/work/03-decision-options.md`. Updated 2026-10-05, after 23:30 UTC, by Fixer B with the infrastructure-feasibility vetting (`architecture/work/05`–`10`): changed recommendations in D2, D3, D5–D13, and the new D15 and D16. The change log is `architecture/work/11b-phase2-feasibility-changelog.md`.

**Status values:**
- **frame-decided:** settled by the captain's frame.
- **decided by the captain:** an answered D-decision, relayed by the lead on 2026-10-05.
- **build choice:** decided by the architecture, inside the frame.
- **pending captain:** the recommended default stands until the captain answers. A different answer changes values and live steps, not components.

| D | Decision | Chosen or recommended option | Status | One-line rationale |
|---|---|---|---|---|
| D1 | The app: form and hosting of the dashboard and its backend | The CLI `prooflab query` is the control test (one engine). It renders one static, self-contained HTML dashboard (ledger, control test, six questions) from the exported snapshot. No server, no network, no public endpoint | Build choice; what goes into the upload: pending captain | Judges read the bucket, not our laptop, so the app must travel inside the pack. A static page can't leak an endpoint, and keeping all verdict logic in the CLI keeps one evaluator |
| D2 | C16: the floor, the one in-path question, the tally | The floor is EP-2, post-run over `aws/spans` (authoritative). The bonus is EP-1: reserve-then-commit before each model call against a frozen, version-stamped cap pinned in env. The tally is carried run-wide by the script. Modes `enforce` / `observe` (an EP setting) with a declared safety ceiling, **recommended ≤ about 300K and always on**, the halt proven on a low test cap before any S2-class run. Tiers from a risk matrix are optional | Shape frame-decided; caps, tiers, safety ceiling and test budget pending captain | Only a per-call check in our own runtime can stop an S2-style loop in time. The gateway figure stays the figure of record, so a forged or drifting tally can't hide a breach. The live-lane budget (about 37–45 runs, 2.5–4.3M tokens, a peak hour of about 1.2M against 2.5M/h) holds only with the ceiling ≤ about 300K (08 LB-01, LB-04) |
| D3 | C9: metric, statistic, window, baseline, alerting | M1: AgentCore invocation Latency Maximum per runtime, plus Errors Sum and invocation counts, per run, with a **two-sided** limit: a model swap can make a runtime faster as well as slower (04 E-07). A declared warm-up rule, because every invocation is a new microVM and cold start sits inside Latency (05 AR-23; 04b B13). Window W2 per run, plus an hourly roll-up. Baseline: 6 post-freeze runs frozen in `v1.1`. Continuous layer: a near-real-time loop (`prooflab watch`) every few minutes alerts within minutes; labelled near-real-time, not in the path. M2 (gateway per-call duration) and M3 (disposition match) recorded as diagnostics. Pilot P8 measures whether a model swap moves them | Pending captain | M1 is AWS-written, caught the only runaway seen so far (278 s vs 11–48 s), and answers per-run questions. Whether it catches the model-swap breach is unproven, so the pilot measures that before the metric is fixed |
| D4 | C7: expected events, event set, gap rule | Expected: gateway actions in `aws/spans`, refusals from `/modaas/evidence`, and a workflow spec frozen in the register (after-stop events included). Observed: only records emitted by the acting adapter at action time. G-a gap judged on the agent clock; G-b recording latency as a diagnostic | Build choice; the coverage, gap and tolerance values come from the owner | The expected set must come from outside the graded agents. Counting pulled observations as observed would make coverage 100% by construction |
| D5 | Registry: source of truth, hand-out, date proof | `register.yaml` in the kit's flat format (extended flat keys; nothing after the last control) → `register/versions/<v>.yaml` + sha256. In-path copy pinned in AgentConfig env at deploy (H1); off-path loads with a sha check (H4). Date proof: **T1, a write-once object in the versioned evidence bucket, dates the threshold; T2, the owner's ServiceNow approval record (not a Finding), corroborates.** The control test checks T1 against the run's first span time; a late or missing T2 is a gap, not INDETERMINATE (04 E-04). Versions are per control (04b A2) | Pending captain | The kit's parser and `submit.sh` dictate the file. AWS- and ServiceNow-set timestamps are ones we don't control, which answers "we check the date" for a stranger. T1 is fail-safe without Object Lock: an overwrite only moves LastModified later, so tampering reads INDETERMINATE, never a false pass (06 D2). Making T1 alone sufficient keeps one late ServiceNow write from turning every verdict INDETERMINATE |
| D6 | The second enforcement point | The same c16 core (`prooflab/evaluators/c16_core.py`, same sha256, embedded byte for byte in each single-file agent) behind EP-1 (`evaluate`, in our runtime) and EP-2 (`pull`, the managed gateway's log, replaying `decide_inline` per gateway call), with an adapter-diff note; the judge's own re-run from the pack is a free third placement. A scheduled ~60 s pull is optional (ARCHITECTURE §3.4, §11) | Build choice | It meets "the same architecture, moved, with nothing rewritten" with code we control, and labels EP-2 honestly as observe-only |
| D7 | Agents | A **new `ifabric-` trio** (`ifabric-customer`, `ifabric-it`, `ifabric-network`) cloned from the reference agent and built by the Module 7 path, all on `nemotron-super-120b`. Judgment J2: structured output checked by code (build choice: JSON in the text answer, with one re-ask; forced structured output only after spike S-5), with deterministic precedence rules. Real evidence emission. The reference trio stays untouched as the "before" system. **Build facts (build choices):** the kit's build ships one source file, so each agent is **one self-contained file**, `ifabric-<role>.py`, with the vendored modules embedded byte for byte, under the 24,049-char gzip+base64 budget (CI gate ≤ 24,000), tested in a local arm64 Docker run before CodeBuild, and always built with a unique `IMAGE_TAG` (a bare `agent.py` overwrites the reference trio's tag) (05 AR-03, AR-05). A 4th agent (the iFabric Assurance agent, handoff-3) is pending integration; the same constraint applies | **Decided by the captain** (2026-10-05) | Our runtime is the only team code in the path. Closing the judgment gap and emitting platform-corroborated evidence are both judged pillars. As first designed, a multi-file agent would have built, approved and gone READY, then failed on its first invocation |
| D8 | The one append-only evidence store | The platform ledger (`audit-store`) is the one live store. **Whether the platform's decisions are appended to it is D16.** The stitched snapshot is the Evidence Pack the tools query offline, uploaded to the versioned bucket with a MANIFEST. Optional: an AWS-timestamped mirror (witness only); its runtime half is now free, because our stdout lines land AWS-timestamped in the runtime's `[runtime-logs]` streams (OC-9 closed; 05 AR-24, 06 B10); only a laptop log group would be an AWS write | Store frame-decided (lead's reconciliation); D16 and the mirror pending captain | Every adapter can reach the ledger (the laptop's POST path is spike S-1), it takes any JSON and it has no update or delete route. Its limit is the server: single-threaded with 256Mi, so exports are per CID and never a full GET during a run (06 C5). The mirror would add a copy no participant can delete, for corroboration |
| D9 | Named PASS and BREACH runs | **On the same `ifabric-` agents, under one frozen version.** C16: PASS = S1 (`enforce`). BREACH = S2 (a) natural, or (b) with a declared `conflicting-context` condition, in `observe`. Re-test = the identical run in `enforce`, halted at the cap (the inline bonus). C7: BREACH = a declared suppressed record; re-test = a full run. C9: BREACH = a model swap behind `ifabric-it`; re-test after the revert. ESC proof = S3. **The C16 breach path is decided by the experiments:** pilots P5–P7 show whether (a) or (b) exceeds the cap; if neither does, C16 is reported "built properly, no breach demonstrated" and C7 becomes milestone 1 (04b B12). The organisers' twin fix adds no lever: the agents' twin is unchanged (09) | Same-agents constraint **decided by the captain**; levers pending captain (recommended: decided by the pilots) | It shows detection and prevention with one evaluator and threshold, and closes each finding with a passing re-test. Every breach is declared before any assessed run, and the cap is never tuned to force one |
| D10 | Guardrail layers per enforcement point | **D10-A, revised after the vetting (ARCHITECTURE §6):** four layers. (1) The gateway's Bedrock guardrail, fixed per model alias and observed: we can't create, edit or choose one (07 GS-15, GS-16). (2) In-agent rails that record; whether any may block is the captain's call, raised by the guardrails design (`architecture/guardrails/02` §0), because a blocking rail is a second waiting question. (3) A Cedar `forbid` on an existing ToolConfig (D15). (4) The C16 guard. Not available: an adopt-mode ToolConfig (GS-03), per-agent Cedar (GS-27), TLS (GS-25: a self-signed placeholder certificate); and an AgentConfig pause is a record, not a stop (GS-14). D10-B (our own ModelConfig guardrail) stays possible but costs a new model alias (SP-3). Identity, approvals, ledger integrity and TLS stay documented gaps | Pending captain | The platform's EPs refuse on their own; within our rules, Cedar on a ToolConfig is the one live lever we can configure (no Cedar text has been edited live yet: SP-1 is the first). Bedrock guardrails are closed to us, and a second waiting question stays excluded until the captain says otherwise |
| D11 | Where adapters, evaluators, the stitcher and the query tool run; credentials | P3 split: the runtime holds the in-path adapter and the agent emits. The laptop (WSParticipantRole) is the hub for the script, collectors, stitcher, evaluators, query tool and ServiceNow glue. The IDE serves person-run reads only (bucket versions); it is not team-exclusive (the organisers ran shell commands on it, 09 §7), so the pack is built on the laptop. CloudShell is the fallback. ServiceNow credentials stay on the laptop (a mode-600 file outside the repo), never in AgentConfig env, and are needed **by about 03:30 UTC**. The AWS credentials are issued for 12 h and expire 2026-10-06T06:29:19Z: **one refresh in 03:30–06:29 UTC** covers the deadline (08 OP-01) | Pending captain (ServiceNow credential placement, refresh duty) | Only the participant role can run Logs Insights on `aws/spans` (the IDE role can't). The runtime role has no read access to logs and no S3 access. A refresh before 03:00 would expire before 15:00; a ServiceNow terminal off the laptop would make every `notify` wait for Arth (08 SN-12) |
| D12 | Record schema and stitch keys | R1: flat dotted keys, a superset of the slide's evidence record plus the captain's metadata. `record_kind` enum; `null_reasons` for table-A fields; deterministic ids for pulled records. Stitch order: CID → action id → trace id → handoff id → **the AWS invocation record, joined exactly by its baggage CID + `runtimeSessionId`** (its `eventTime`, the call's end, matched to `handoff.received`; two records with one session id flagged as a retry) → finding id. `aws.request_id` stays null: the CLI never exposes it. The AWS model-call records (`Converse*`) carry no ids and join by time, role and model only (10-f11, settling 03 F11 in favour of 05 AR-20) | Build choice | It stays closest to the slide and to the ledger's `correlation_id` filter, and one schema from every adapter is what "nothing rewritten" looks like. Key 5 was an ARN + time-window guess; the AWS-written record turned out to carry the caller's ids in `responseElements` on 28 of 28 records |
| D13 (new) | The optional pre-run version gate (EP-0), from the captain's request to make the pre-deployment, continuous and post-deployment control layers explicit | Before each run, the orchestrating script checks each agent's running version against an approved version: model alias + generation + runtime version (a model swap changes env, not the image digest, and the reference agents share one digest), approved per the `ApprovalRecorded` notification's `observedGeneration`, corroborated by the AWS Agent Registry's `updatedAt` and the runtime version history; or a treatment declared in the register with the owner's approval record. It also declines a run on a paused AgentConfig, because a pause doesn't stop direct invocations (07 GS-14). It **blocks ASSESSED runs** on a mismatch and **only records** for every other run. It never reads env values (filtered field paths, OC-19 closed). Live today it would flag the reference IT and network agents: generation 2 on a generation-1 approval (07 GS-22) | Pending captain (the lead's recommendation: block assessed runs) | It answers APPROVED and gap 5 before anything runs, because the platform adds no approval record on a swap. It sits before the run, so the one in-path question stays the only wait inside a run |
| D14 (new) | Where the AI inventory (`inventory.yaml`) and the risk register (`risks.yaml`) live, from the captain's request to add risk and ownership (ARCHITECTURE §3.9, §3.10) | **Recommended:** repo YAML in `register/` is the source the evaluators, the stitcher and the query tool read. `risks.yaml` is frozen and dated with `register.yaml` (one version, one S3 write-once proof, one owner approval naming both sha256s); `inventory.yaml` is frozen as `inv-N` on each change; both go into the pack. Arth mirrors the AI system, its owners and its risk tier into ServiceNow AICT (`Managed by`, `Risk classification`) for L2/L3. **Alternatives:** (b) repo only, no mirror; (c) AICT as master, exported into the pack before judging | Pending captain (the architect's recommendation) | The judge's offline control test and the version gate need a frozen, dated, hashable file in the pack. AICT can't give that: its "Approved" is an editable Status with no approver, time or version link, and discovered assets arrive with no owner. The mirror still puts owners and the tier where the L2/L3 judges look. (b) gives up that showing; (c) would make the gate depend on a field nobody can date. Whether Arth's account can set the AICT fields is an open check (OC-23) |
| D15 (new) | The Cedar demo path: where a Cedar `forbid` can refuse a governed tool call, within our rules (from the governance vetting, `work/07`; ARCHITECTURE §6.2) | **(a) Recommended:** edit an **existing** ToolConfig's `spec.access.cedarPolicy` (for example `customer-records`): one narrow `forbid` keyed on a declared test value no scenario uses, every attribute guarded with `has`, never a custom `policyId`. Spike SP-1 applies it before the agents' freeze, makes one allowed and one forbidden call, and checks both PDP replicas and `/modaas/evidence`; the original text is restored before the final snapshot. It applies to every caller (one shared principal), so it needs the captain's OK and the user's explicit OK. **(b)** Relax the no-Lambda / no-gateway-write rule. Its least invasive form is a custom `ifabric-` MCP tool from the kit's template (07 GS-01/02: no Lambda and no AWS write, but the tool operator writes a new route on the shared gateway, and a delete leaves a projected ConfigMap and a DEPRECATED registry record we can't remove, GS-26); a new Lambda or AgentCore-gateway target (GS-04/05) would also need the organisers. **Removed:** an `ifabric-` ToolConfig adopting an existing gateway target (GS-03) | Pending captain | Authz picks the policy from the wire tool name `<target>___<tool>`, so for an existing tool only that tool's own policy can refuse its `tools/call`; an adopt-mode ToolConfig never decides one. (a) needs no build, no Lambda and no gateway write, and gives the platform's first Cedar DENY for ADV-R-01. Its costs, every caller and a shared asset, are why it needs the captain. The user's earlier direction allows Hostile and Rogue tests to modify ToolConfig Cedar |
| D16 (new) | "One store", literally: is every decision, the platform's included, recorded in the one evidence store? (from the adversarial review, `work/04` E-01; ARCHITECTURE §3.2, §3.5) | **(a) Recommended:** the platform ledger, with **every adapter writing to it**: our records at action time, and the platform's decisions appended by the pull adapters as normalized `platform_decision` records (deterministic `record_id`, so re-pulls deduplicate; `source.refs` to the raw line and its sha256; the raw capture stays the authority), between runs only. It depends on spike S-1 (the laptop's POST path) and on per-CID exports. **Fallback (b):** a normalized store on the laptop for the platform's decisions (the snapshot's derived records), with the ledger holding only our records, and every "one store" phrase reworded to match | Pending captain | The frame says every decision is recorded in one evidence store, and a judge may ask to see a Cedar DENY "in your ledger". (a) makes that literally true and makes the append-only test runnable on the platform's decisions too. Its risks are the single-threaded 256Mi server (no full GET during a run; about 20–30K records before a full GET risks the memory limit, 06 C5) and an unproven POST path until S-1 passes; (b) keeps the ledger small but needs the wording changed everywhere |
